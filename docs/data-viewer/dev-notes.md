# data-viewer 開発メモ

## 実装上の判断

| 判断内容 | 理由 |
|----------|------|
| **Excel を直接読むのをやめ、変換したあとの C# のデータベースを見る**（2026-11-13。機能名を sheet-db から data-viewer に変えた） | Excel を直接見る理由は書き戻しだった。書き戻しをしないなら、変換したあとのデータを見れば足りる（利用者の判断）。xlsx の読み込み・キャッシュ・ブックの監視が要らなくなった。前の設計は commit a2d9fd2 にある |
| 参照だけで、編集しない | 利用者の決定（2026-11-13）。正本は変換のもとにあり、エディタで変えても変換し直すと消える |
| 変換は含めない | 利用者の決定（2026-11-13） |
| ランタイムには出さない | `docs/project_overview.md` の方針どおり |
| データの入れ物の形に依存しない（ソースを差し替えられる） | 利用者がまだ決めていない（2026-11-13）。ScriptableObject のアセットなら組み込みのソースで、独自のファイルなら利用者が書くソースで受ける |
| **主キーと参照は、設定だけで指定する**（名前の規則で推測しない・属性を求めない） | 利用者の決定（2026-11-13）。属性を使うと、パッケージにランタイムのアセンブリが要る |
| 設定はフィールドの名前で書くので、名前が変わると黙って外れる。これを問題として報告する | 設定だけで指定する方式で、一番起きやすい壊れ方 |
| 列は Unity がシリアライズするフィールドと同じ規則で選ぶ | エディタが見せるものと、実際に保存されているものを一致させる |
| 規模と目標は sheet-db のときの「標準」を引き継ぐ | 利用者の決定（2026-11-12）。値は `spec.md` の性能の目標にだけ書く |
| 取り出しはメインスレッド、索引はスレッドプール | ユーザーのオブジェクトは、メインスレッドから書き換わることがある。取り出したあとの配列は、どのスレッドからでも読める |
| キャッシュを持たない | 取り出しが速い（下の「確認の方法」）。アセットの読み込みが遅いときは、ビューアのキャッシュではなく、データの持ち方（アセットを分ける・バイナリで保存する）で解決する |

## 確認の方法

### 設計の前に測ったこと（ホストの Unity 6000.3.28f1、Mono）

**2026-11-13: リフレクションでの取り出し。**MCP の `script-execute` で、10 フィールド（int 8・float 1・string 1）の struct を 10 万要素持つ `List` を作り、全フィールドを読む時間を比べた。

| 方法 | 結果（2 回） |
|---|---|
| `IList` の要素ごとに `FieldInfo.GetValue`（箱に入る） | **測った**: 286 ms・253 ms |
| 式木でコンパイルした `Func<object, int, object>`（行ごと・列ごと。箱に入る） | **測った**: 93 ms・94 ms（コンパイル 8 ms・1 ms） |
| 式木でコンパイルした、1 列を `int[]` に詰めるループ（箱に入らない） | **測った**: int の 8 列で 12 ms・12 ms（コンパイル 24 ms・2 ms） |

- `string`・`float`・`enum` の列の取り出しと、文字列表への集約の時間は測っていない（**推測**: 同じ程度。fixtures I-02 で測る）
- 開発用プロジェクトのアセットはテキストで保存される（`EditorSettings.asset` の `m_SerializationMode: 2`）。10 万行の ScriptableObject を読み込む時間は測っていない。fixtures I-03 で測る

**2026-11-12（sheet-db のとき）: xlsx の読み込み。**BCL だけで 2 万行 × 10 列を約 240 ms で読めた。いまは使わないが、変換を作るときに参考になる（commit 2ebe12a の `docs/sheet-db/dev-notes.md`）。

| 確かめること | 方法 | 対照 |
|--------------|------|------|
| 性能の目標 | fixtures I-02〜I-06 を MCP 経由で走らせる | 各テストの対照（当たる件数が 0 でない、など） |
| 設定の食い違いの検出 | settings U-03〜U-05 | 食い違いのない設定では問題が 0 件 |

## 今後の課題

- 「大きめ」の規模（100 万行）にするときは、目標と fixtures の規模を変えて測り直す
- 複数の値を持つフィールド（`int[] ability_ids`）を参照として扱うこと
