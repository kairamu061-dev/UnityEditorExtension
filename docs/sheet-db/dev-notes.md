# sheet-db 開発メモ

## 実装上の判断

| 判断内容 | 理由 |
|----------|------|
| 正本は xlsx。Unity は参照だけで、編集は Excel で行う | 利用者の決定（2026-11-12）。書き戻しを外すと、書式・数式・列幅を保ったまま xlsx を書く処理（全体で一番難しい部分）が要らなくなる |
| ランタイムには出さない | 利用者の決定（2026-11-12）。`docs/project_overview.md` の方針どおり |
| 規模と目標は「標準」（10 万行・50 ブック・最大 2 万行。開く 0.5 秒・検索 50 ms・ジャンプ 16 ms） | 利用者の決定（2026-11-12）。値は `spec.md` の性能の目標にだけ書く |
| スキーマは各シートの 1・2 行目に書く。別のスキーマのシートやファイルは作らない | テーブルと型の定義が同じ場所にあれば、Excel で編集するときに食い違わない。列を足すとき、1 か所を直せば済む |
| 1 列目を主キーにする | 決まりが 1 つで済み、Excel で見たときにも分かりやすい |
| xlsx の読み込みは自作する | 外部パッケージに依存しない制約。BCL だけで足りることを測った（下の「確認の方法」） |
| Core（読み込み・スキーマ・索引・キャッシュ）は `noEngineReferences` | スレッドプールで動かすため、Unity の API を呼べない作りにしておく。未決の `dotnet test` の CI 案にもそのまま載る |
| 表示と検索の派生データ（数値の表示の文字列・小文字の写し）は、読み込みのときに作る | Database を作ったあとで書き足すと、検索や描画のスレッドが共有の状態を書き換えることになり、丸ごと差し替える方式（ロックなし）が崩れる。読み込みは裏で行うので、作る時間はエディタを止めない |
| キャッシュに「解釈の版」を持たせる | ファイルの形が同じでも、パッケージを上げて読み方が変わると、古い読み方の結果がキャッシュから出続ける |
| 共有文字列のふりがな（`<rPh>`）は読まない | 日本語の IME で入力したセルに Excel が付ける。読むと値にふりがながくっつき、前から順に `<t>` を拾う読み方では、後ろの文字列の番号もずれる |
| 変更は `FileSystemWatcher` で見張らず、エディタに戻ったときに調べる | 見張りのイベントは別のスレッドで来て扱いが難しい。50 冊の大きさと更新時刻を調べるのは軽い（**推測**。fixtures I-06 で測る） |

## 確認の方法

### 設計の前に測ったこと（2026-11-12、ホストの Unity 6000.3.28f1、Mono）

使い捨ての asmdef（`overrideReferences: true`・`precompiledReferences: []`・`noEngineReferences: true`）に、`ZipArchive` と `XmlReader` で xlsx を読む試作を置いて測った。終わったあと、試作は消し、API 互換レベルも元に戻した。

| 確かめたこと | 結果 |
|---|---|
| API 互換レベル .NET Standard 2.1（開発用プロジェクトの設定）でコンパイルできるか | **測った**: できる。コンソールのエラー 0 件 |
| .NET Framework に切り替えてもコンパイルできるか | **測った**: できる。参照されたアセンブリは `mscorlib, System, System.IO.Compression, System.Xml`。`csc.rsp` などは要らなかった |
| 読む速さ（合成の 2 万行 × 10 列、共有文字列と数式を含む、1.27 MB） | **測った**: .NET Standard 2.1 で 233・255・239・253 ms（共有文字列 13〜23 ms、シート 220〜242 ms）。.NET Framework で 248 ms |

- 合成データは Python の `zipfile` で作った（`[Content_Types].xml`・rels・workbook・シート 1 枚・共有文字列）。fixtures の生成器は同じ形で C# で書く
- **推測**: 10 万行を 1 本のスレッドで読むと約 1.2 秒。並列にすれば短くなるが、それでも「開く 0.5 秒」には届かない。だからキャッシュを最初から設計に入れた

| 確かめること | 方法 | 対照 |
|--------------|------|------|
| 性能の目標 | fixtures I-02〜I-06 を MCP 経由で走らせる | 各テストの対照（当たる件数が 0 でない、`Parsed == 1` など） |
| 実物の Excel の形 | xlsx-reader I-01（コミットした実物のブック） | — |
| Excel が開いているブックを読めるか | xlsx-reader E-01 | `FileShare.None` で開くと失敗すること |

## 今後の課題

- 「大きめ」の規模（100 万行）にするときは、目標と fixtures の規模を変え、キャッシュの読み戻しの時間を測り直す
- 列の型を足す（`enum`・日付など）。足すときは schema と cache の形式の版を上げる

## ユーザへの要望

- **xlsx の読み込みを、別のパッケージ（`com.obelune.xlsx` など）に分けるか。**ほかの拡張機能でも xlsx を読むなら、分けておくと再利用できる。いまは `Obelune.SheetDb.Core` の中に置き、名前空間を分けておく（あとから取り出せる）
- **データフォルダは `Assets/` の外に置くことを勧めたい**（例: プロジェクト直下の `Data/`）。`Assets/` の中に置くと、Unity が xlsx と Excel の一時ファイル（`~$`）を取り込み、`.meta` を作る（**推測**。実際に作られるかは未確認）
- 実物の Excel で作ったテスト用のブック（xlsx-reader I-01・親の E-01）は、Excel で保存したものが要る。作ってもらうか、作り方の指示を出すので、それに沿って保存してほしい
